Agent Gateway API Reference

Last updated: 2026-10-01 · Epic: MVP-2453 · GitHub

The Agent Gateway is a standalone REST API service wrapping the Claude Agent SDK. It exposes Claude Code's agentic capabilities (Bash, Read, Write, Edit, Glob, Grep, WebSearch, WebFetch) over HTTP with NDJSON streaming, session management, workspace file CRUD, and automatic retry with exponential backoff.

Authentication

All endpoints except /health require a Bearer token. API keys are configured via the API_KEYS environment variable as comma-separated label:secret pairs.

# .env
API_KEYS=myapp:sk-gw-abc123,cicd:sk-gw-def456

Send the secret as a Bearer token in the Authorization header:

Authorization: Bearer sk-gw-abc123

The label (e.g., myapp) appears in server logs for audit purposes, scopes sessions, the event cache and registered tools, and is the key of AGENT_TOOL_POLICY (see Tool Mediation). On invalid or missing credentials, the API returns 401:

{"error": "Missing or malformed Authorization header"}
{"error": "Invalid API key"}

Health Check

GET /health No Auth

Returns server status, version, uptime, active session count, and whether the three state files (sessions.json, tools.json, mcp-servers.json) are being saved normally. The HTTP status is always 200 and status stays "ok"; persistence and persistenceIssues are additive.

Response

{
  "status": "ok",
  "version": "0.1.0",
  "uptime": 3600,
  "sessions": 2,
  "isolation": "ok",
  "persistence": "ok",
  "persistenceIssues": []
}

isolation is "ok" once a sandbox has started and passed its check, "unavailable" after a permanent start problem (agent runs are refused until a later start succeeds) and "starting" while the boot self-check runs. The compose health check requires "ok". See Agent Isolation.

Response (degraded)

{
  "status": "ok",
  "version": "0.1.0",
  "uptime": 1,
  "sessions": 0,
  "isolation": "ok",
  "persistence": "degraded",
  "persistenceIssues": [
    {
      "area": "mcpServers",
      "problem": "corrupt-preserved",
      "file": "/home/node/.claude/mcp-servers.json",
      "preservedAs": ["/home/node/.claude/mcp-servers.json.corrupt-20260926T213634Z"]
    }
  ]
}

persistence is "ok" exactly when persistenceIssues is empty. area is sessions, tools or mcpServers; several entries may be listed, also for the same area. preservedAs is present only for corrupt-preserved. The compose healthcheck only checks for a 2xx status, so the container stays healthy while degraded: monitoring must read persistence.

curl -N -X POST http://localhost:3001/v1/query \
  -H "Authorization: Bearer sk-gw-abc123" \
  -H "Content-Type: application/json" \
  -d '{
    "queryId": "q-001",
    "prompt": "What files are in the current directory?",
    "sessionId": "session-1",
    "systemPrompt": "You are a helpful assistant.",
    "mcpCredentialOverrides": {
      "jira": {
        "headers": { "Authorization": "Basic <base64(email:apiToken)>" }
      }
    }
  }'

Override server names must exist and be enabled. Unknown names return MCP_SERVER_NOT_FOUND; disabled names return MCP_SERVER_DISABLED. Overrides are merged for that one request only and are never persisted to the MCP registry.

A single query may also attach an unregistered MCP server via mcpServers. The gateway validates and normalizes each entry on the trusted side: the name matches ^[A-Za-z0-9][A-Za-z0-9_-]{0,31}$; agent-gateway-tools is reserved; a server has either command (stdio; it must not set type) or url (type only http or sse; a url without type is http); headers and env must be string maps with sendable values; unknown fields are dropped. A name equal to any registered server (enabled, disabled or left out of the run) answers 400 {"error":{"code":"MCP_SERVER_NAME_CONFLICT","message":...}}; registering a server named like a caller's request server therefore makes those requests fail. Request servers are merged at the lowest precedence (the gateway's agent-gateway-tools and registered servers always win) and are never persisted. reqlift recon uses this to attach a per-run chrome-devtools server.

Routing: http/SSE request servers with headers (or a URL with a user name, password or query) go through the relay (the runtime gets only a relay URL), stdio request servers with env run in their own tool sandbox, and request servers without headers/env connect directly or run inside the agent sandbox. Pass credentials for request servers only through env or headers, never in args or a URL path: the agent can read those. A request command server is code the caller picked: it is attached only when the trusted policy lets the caller's label run Bash (no policy, or Bash not denied) or names that server in its allow list; otherwise it is left out with mcp.server.omitted serverName=<name> reason=command_not_granted.

Enforced Tool Set (enforcedTools)

With enforcedTools a run may call exactly the listed tools (no wildcards). A call to any other tool reaches no handler — no webhook request, no MCP tools/call, no shell command, no fetch — and the model gets an error tool result (the TOOL_DENIED text when the gateway refuses it, or the runtime's own <tool_use_error>Error: No such tool available: <name></tool_use_error> for a built-in it was not offered; that text belongs to the runtime and cannot be changed). The tool_result event carries "success": false. The gateway logs audit tool.denied toolName=<name> queryId=<id>. The run goes on; whether a refusal fails the job is the caller's decision.

Enforcement is layered: no user or project settings from HOME (settingSources: []), permissionMode: "dontAsk" with allowedTools exactly the set, only the listed built-ins offered, agent-gateway-tools and registry/request MCP servers attached only for listed tools, a deny-only PreToolUse hook, and no per-user skill bundle. The effective grant is the policy for the caller's label intersected with the set, so a caller can only narrow: when enforcedTools names a tool the policy denies, the request is accepted, the tool_policy acknowledgment still echoes the requested set, the gateway logs audit tool.policy.narrowed queryId=<id> denied=<names>, and the tool is refused at call time. The first event is {"seq":0,"type":"tool_policy","enforced":true,"tools":[…]}, sent once before any retry; retries keep the set.

Validation (400 before streaming): an array (null is refused) of at most 64 distinct names of 1–128 characters A-Z a-z 0-9 _ -; not with allowedTools; no Task or Agent; no mcp__… name that fits two attachable servers. [] means no tool at all. Without the field the run's tools are the trusted grant (see Tool Mediation).

curl -N -X POST http://localhost:3001/v1/query \
  -H "Authorization: Bearer sk-gw-abc123" \
  -H "Content-Type: application/json" \
  -d '{"queryId": "q-1", "prompt": "Read the page and report each area.",
       "enforcedTools": ["mcp__jira__get_confluence_page", "mcp__agent-gateway-tools__reqlift_confluence_report_region"]}'

Failed Queries

A failed query ends with exactly one error event and no done; it confirms no session. The event keeps its shape {"seq", "type": "error", "content"}, and content is a safe, actionable message for the end user. The Claude runtime reports a provider rejection on its stdout before it exits with code 1; the gateway classifies that diagnostic instead of passing on the runtime's exit message. Raw diagnostics (provider responses, runtime output, stack traces, headers, prompts) never appear in content, in any other event, or in a failure or retry log line at any log level. The debug-level request preview is unchanged and may still contain the client's own prompt.

Multimodal Content (content[])

Send text and images in a single query by passing a content array of content blocks. The array maps directly to the Anthropic API content-block format and is forwarded to the Claude Agent SDK as a structured user message — image blocks are passed through to Anthropic unmodified.

type ContentBlock =
  | { type: "text"; text: string }
  | { type: "image"; source: { type: "base64"; media_type: string; data: string } };
  • If content is a non-empty array, it takes precedence over prompt.
  • If only prompt is provided (backward-compatible path), it is wrapped internally as [{ "type": "text", "text": prompt }] — existing text-only queries are unchanged.
  • Each block is structurally validated; a malformed block (missing source.data, non-base64 source.type, unknown type) returns HTTP 400 before the stream opens.
  • The NDJSON event stream is identical in shape for multimodal and text-only queries.

The JSON request body limit is 25 MB to accommodate base64-encoded images. A body that exceeds the limit is rejected with HTTP 413. Per-image size and per-query image-count limits are enforced upstream by the caller, not by the gateway.

curl -N -X POST http://localhost:3001/v1/query \
  -H "Authorization: Bearer sk-gw-abc123" \
  -H "Content-Type: application/json" \
  -d '{
    "queryId": "q-multimodal-1",
    "content": [
      { "type": "text", "text": "What is shown in this screenshot?" },
      {
        "type": "image",
        "source": {
          "type": "base64",
          "media_type": "image/png",
          "data": "<base64-encoded-image-bytes>"
        }
      }
    ]
  }'

Query Events (Replay)

GET /v1/query/:queryId/events Auth Required

Replays cached events for a query. If the query is still running, the connection stays open and streams new events in real time. Supports resuming from a specific sequence number.

Query Parameters

ParamTypeDefaultDescription
afterinteger-1Only return events with seq > after

Response

NDJSON stream identical to POST /v1/query. The event cache is keyed by API-key label and queryId: only the label that started the query can replay it, and any other label gets 404 Query not found or expired (as does an unknown or expired queryId).

Example

curl -N http://localhost:3001/v1/query/q-001/events \
  -H "Authorization: Bearer sk-gw-abc123"

# Resume from sequence 5
curl -N "http://localhost:3001/v1/query/q-001/events?after=5" \
  -H "Authorization: Bearer sk-gw-abc123"

PUT /v1/settings Auth Required

Updates session settings. Currently supports sessionIdleTimeoutMs.

Sessions

A session is a mapping from a client-provided sessionId to a Claude Agent SDK conversation session. Sessions maintain conversation context — follow-up queries sent with the same sessionId have access to all previous messages in that conversation. Sessions are persisted to SESSION_PERSIST_PATH and survive server restarts.

sessionIdleTimeoutMs

Default0 — disabled, sessions persist indefinitely
Cleanup granularity5 minutes — a background timer runs every 5 minutes and evicts sessions that have been idle longer than the configured timeout. Sessions may therefore exist up to 5 minutes past their timeout.

When set to 0 (the default), no cleanup runs and every unique sessionId stays in memory and on disk forever. This is convenient for long-lived conversational agents but means memory usage grows unboundedly if many distinct session IDs are used.

When set to a value greater than 0, the cleanup timer is activated. Any session that has not received a query within the configured duration is removed from memory and from disk. The next query that arrives with that sessionId starts a fresh session — all previous conversation context is lost.

Request Body

{"sessionIdleTimeoutMs": 3600000}

Response

{"sessionIdleTimeoutMs": 3600000}

Example

# Set 1-hour idle timeout (sessions idle for >1 h are evicted; check runs every 5 min)
curl -X PUT http://localhost:3001/v1/settings \
  -H "Authorization: Bearer sk-gw-abc123" \
  -H "Content-Type: application/json" \
  -d '{"sessionIdleTimeoutMs": 3600000}'

# Disable cleanup — sessions live forever (default)
curl -X PUT http://localhost:3001/v1/settings \
  -H "Authorization: Bearer sk-gw-abc123" \
  -H "Content-Type: application/json" \
  -d '{"sessionIdleTimeoutMs": 0}'

PUT /v1/logging Auth Required

Changes the log level at runtime. Valid levels: off, info, debug.

Credentials in the debug log: at debug the gateway logs request bodies (first 2000 characters) and response previews (first 500 characters). The whole value of every headers and env key, at any depth, is logged as "[REDACTED]" with the keys visible: mcpServers[*] and mcpCredentialOverrides of POST /v1/query, the /test and /call bodies, and MCP server definitions in registry create/update bodies and in the create/update, detail and list answers. The args of a stdio server definition (an object with a command key or type: "stdio") are logged as one "[REDACTED]" per element: a credential can be passed on the command line. At debug the log also holds the request text of every conversation, so it is an operator-only surface. Every sshKey value is logged as "[REDACTED]" and every string under a url key without its credentials (scheme://***@host/..., everything up to the last @), which covers the clone URLs and inline SSH keys of /v1/workspace/git/*. Redaction runs before the cut, so no prefix of a value appears. The API answers themselves are unchanged. text/* request bodies are logged as their length, a non-JSON registry answer is not previewed, and an unparseable JSON body is logged as request body rejected type=<type> status=<code>.

Request Body

{"level": "debug"}

Response

{"level": "debug", "previous": "info"}

Example

curl -X PUT http://localhost:3001/v1/logging \
  -H "Authorization: Bearer sk-gw-abc123" \
  -H "Content-Type: application/json" \
  -d '{"level": "debug"}'

Git Clone

POST /v1/workspace/git/clone

Clone a git repository into the workspace projects directory. If the target path already exists with a .git directory, performs a git pull instead — when branch is supplied, the local checkout is first switched to that branch and upstream tracking to origin/<branch> is set/repaired so the pull cannot fail with "no tracking information".

Request Body

{
  "url": "git@github.com:org/repo.git",   // Required: repository URL
  "path": "my-project",                    // Required: relative path under projects/
  "branch": "main",                        // Optional: branch to clone
  "sshKey": "-----BEGIN OPENSSH..."        // Optional: SSH private key for auth
}

Response (200)

{
  "status": "cloned",    // or "pulled" if target already existed
  "path": "my-project",
  "branch": "main",
  "commit": "a1b2c3d"
}

Errors

  • 400 {"error": "url is required"}, "path is required", "Invalid path (must be relative, no traversal)"
  • 400 {"error": "Invalid branch"} — branch starts with -; nothing is queued and no git process starts
  • 400 {"error": "Invalid url"} — url contains a line break or NUL; nothing is queued and no git process starts
  • 400 {"error": "<field> must be a string"} — url, path, branch or sshKey is present but not a string (pull: path, branch, sshKey); nothing is queued and no git process starts
  • 500 {"error": "<git's message>"} — git's own error output with URL credentials hidden: on each line, everything from the first scheme:// to the last @ appears as ***, so the user:password@ part of an http:// or https:// URL stays hidden whatever characters the token contains (a host or path on the same line may be hidden too). ssh://, git:// and file:// URLs do not use passwords, and ssh or git may repeat their user:password part in a form this redaction does not catch.
  • 500 {"error": "git <subcommand> timed out after <n> s"} — a git command exceeded GIT_TIMEOUT_MS (default 120 s)

Queueing

Git runs without blocking the gateway: /health and running streams keep answering. Clone, pull and status requests for the same path run one at a time in arrival order, and a queued request sees the previous one's result (a second first clone of the same path answers "pulled"). At most GIT_MAX_CONCURRENCY (default 3) operations run at once overall; further requests wait in arrival order and are never rejected. Arguments go to git without a shell, so values are used literally.

Security

SSH keys are written to a private temp directory (key file 0600) only once the request's git operation starts, and deleted immediately after it, whether it succeeded, failed or timed out. Keys are never persisted on disk. The key never appears in error text or in the gateway log. The user:password@ part of an http:// or https:// URL does not appear in error text or in the gateway log at any level, whatever characters the token contains, including /, whitespace, quotes and @ (a token in a query string is not redacted). ssh://, git:// and file:// transports do not use URL passwords; ssh or git may echo such a URL's user:password part (for example Could not resolve hostname user:<password>) where the redaction cannot see it, so put tokens only into http(s):// URLs.

  -d '{
    "url": "git@github.com:org/repo.git",

POST /v1/mcp-servers/:name/uploads/* Auth Required

Streams a raw file upload to a registered http/sse MCP server, with a per-call credential. The gateway is a dumb pipe: it does not parse, buffer, store or log the file. Each received chunk is forwarded and dropped; a slow MCP server slows the sender down (backpressure end to end). The request is forwarded as POST <origin of the registered url>/uploads/<target>?<query> and the MCP server's status (200–599) and body come back verbatim (for mcp-jira: 201 { attachmentId, mediaApiFileId, filename, size } or its own error codes such as 401 UPLOAD_UNAUTHENTICATED).

Request

POST /v1/mcp-servers/jira/uploads/jira/issue/MVP-1?filename=shot.png
Authorization: Bearer <gateway API key>
X-MCP-Credential-Headers: <base64 of {"Authorization":"Basic <base64(email:apiToken)>"}>   (optional)
Content-Type: image/png
Content-Length: 5242880
<raw bytes>
  • Path and query are taken from the raw request URL and forwarded byte for byte. The target is refused (400 UPLOAD_TARGET_INVALID) when it is empty, has a . or .. segment (also as %2e), or contains %2f, %5c or a backslash. Host and port come only from the registration.
  • X-MCP-Credential-Headers: one header, canonical base64 of a UTF-8 JSON object of string values (no CR, LF, NUL; no keys that differ only in case). Only Authorization is used, and it must be printable ASCII; it replaces a registered Authorization. The header itself is never forwarded or logged.
  • Forwarded headers: the override Authorization, the registered static headers (minus Host, Content-Length, Content-Type, Transfer-Encoding, Connection, Keep-Alive, Upgrade, TE, Trailer, Expect, Proxy-*), and the incoming Content-Type / Content-Length. A chunked request is forwarded chunked. Static headers of any http/sse registration therefore also reach <origin>/uploads/ (relevant for servers behind a path-routing proxy). The gateway's own Bearer key is never forwarded.
  • The body is never read by the JSON/text parsers, whatever its Content-Type.

Example

CREDENTIAL=$(printf '%s' 'user@example.com:<api-token>' | base64 -w0)
curl -X POST "http://localhost:3001/v1/mcp-servers/jira/uploads/jira/issue/MVP-1?filename=shot.png" \
  -H "Authorization: Bearer sk-gw-abc123" \
  -H "Content-Type: image/png" \
  -H "X-MCP-Credential-Headers: $(printf '{"Authorization":"Basic %s"}' "$CREDENTIAL" | base64 -w0)" \

Timing, aborts and resources

  • MCP_UPLOAD_IDLE_TIMEOUT_MS is a no-progress timeout, not an overall deadline: a slow upload completes while it progresses. Node's server-wide requestTimeout is 3600 s; every other route keeps a 300 s deadline for its request body until the gateway has answered.
  • A sender disconnect aborts the upstream request at once. An early answer of the MCP server (before the whole body was sent) stops forwarding and is passed through.
  • Every answer on this route carries Connection: close. When the gateway answers while the sender is still sending (any refusal, including the 401), it discards at most 1 MiB more and closes the connection when the sender closes it or 5 s after the answer.
  • The relay returns to the event loop after every forwarded chunk, so an early answer is normally read before more is written, even from a fast sender such as curl. An MCP server can still reset the connection before the gateway has read its early answer: mcp-jira refuses a missing credential at once and closes after reading at most 1 MiB more, with the rest of the body unread, which makes the kernel reset the connection. The gateway's next write then fails; it stops sending and keeps reading for at most 1 s, so an answer that had already arrived (for example 401 UPLOAD_UNAUTHENTICATED), also one whose headers and body came in separate segments, still reaches the sender unchanged; without an answer the sender gets 502 "unconfirmed". The gateway sends the answer's status line to the sender only together with the first answer byte: headers received from the MCP server are not yet bytes sent to the sender. An answer that breaks off after its headers but before any byte reached the sender ends as a complete 502 "unconfirmed" (its own Content-Type and Content-Length, never the MCP server's status); one that breaks off after bytes reached the sender stays truncated, with no replacement status. Measured under deliberate CPU load with http MCP servers, both this close and a connection kept open until the sender stops delivered every early refusal unchanged. Limits: https MCP servers were not measured; reading after the failed write relies on Node stream internals, and if a Node version no longer allows it the gateway falls back to 502 "unconfirmed" for this case and the upload relay process tests fail.
  • No size or concurrency cap in the gateway: reqlift's 100 MiB cap applies to reqlift callers only; other key holders are bounded by the MCP server (Jira's attachment limit). Memory stays flat per upload: the test suite asserts a 50 MB relay raises the peak resident memory by less than 10 MB, with node --expose-gc (set in entrypoint.sh) forcing a minor GC every 2 MiB relayed.
  • Nothing is written to disk. The request log line carries the URL (target and file name), never file bytes or the credential; one audit line per relay: mcp.upload.relayed serverName=… status=… bytes=… result=ok|upstream_answer|upstream_failed|timeout|client_aborted.

Webhook Execution Flow

When the Claude agent invokes a registered tool during a query, the gateway POSTs to the tool's webhook_url:

1

Agent invokes tool

The Claude agent decides to use a registered tool (e.g., lookup-customer) based on its description and input schema.

2

Gateway POSTs to webhook

The MCP server handler sends a POST request to the tool's webhook_url with the following body:

{
  "tool_use_id": "tu_abc123",
  "tool_name": "lookup-customer",
  "input": { "email": "user@example.com" },
  "context": {
    "user_id": null,
    "conversation_id": null,
    "session_id": "session-1",
    "api_key_label": "myapp"
  }
}

The calling client's Bearer token is forwarded in the Authorization header, only to tools its own label owns (a legacy tool without an owner keeps this until it is registered again, with the audit line tool.webhook.legacy_forward toolName=<name> per call; a tool of another label never gets it). The X-Webhook-Context header comes only from the authenticated request; tool input keys such as context or user_id stay in the body. The webhook call never follows a redirect, and a run is offered only its own label's tools plus legacy ownerless ones.

3

Webhook responds

The external service processes the request and returns:

{
  "output": "Customer found: Jane Doe, Plan: Enterprise",
  "metadata": { "customer_id": 42 }
}

On error (timeout, HTTP error, network failure), an error result with one of the fixed TOOL_* texts is returned to the agent, which can retry or use an alternative approach; the event carries "success": false. At startup the gateway logs tools.legacy.ownerless count=<n> for entries without an owner.

4

Agent continues

The tool result is passed back to the Claude agent as a tool_result event, and the agent continues its work.

MCP Server Registry

The MCP Server Registry registers external MCP servers that are injected into every Claude Agent SDK query. Definitions persist to MCP_SERVERS_PERSIST_PATH and support http, sse, and stdio transports.

PUT /v1/mcp-servers/:name Auth Required

Registers a new MCP server or updates an existing one. Returns 201 for new servers and 200 for updates. The calling API-key label becomes the server's owner when it creates the entry; only the owner can change or delete it afterwards (Registry ownership).

Output templates support plain substitution such as {fieldKey} and prefix-{a}-{b}, plus Basic auth templates such as basic:{email}:{apiToken}, emitted as Basic <base64(email:apiToken)>.

Server name rule: a PUT that creates a new entry needs a name of 1–32 letters, digits, - or _, starting with a letter or digit (^[A-Za-z0-9][A-Za-z0-9_-]{0,31}$; the Agent SDK builds tool names as mcp__<server>__<tool> without shortening them). Any other new name answers 400 with {"error":{"code":"MCP_SERVER_NAME_INVALID","message":"Use 1–32 letters, digits, '-' or '_', starting with a letter or digit."}} before any other check, and nothing is stored. An existing entry is never refused because of its name: updating it with PUT and DELETE still work, so an entry created before this rule can be edited, switched off or removed.

Validation: headers and env must be string maps; every header must be one Node can send (token name, no CR, LF, NUL or other invalid character in the value) and env names and values must not contain NUL. Violations answer 400, e.g. {"error":"headers holds a name or value that cannot be sent as an HTTP header"}. A non-boolean requireUserCredentials answers {"error":"requireUserCredentials must be a boolean"}; true with type: "sse" answers {"error":"requireUserCredentials is not supported for sse transport"}.

Stored headers and env are write-only (MVP-7936): the reply of a successful PUT (201 and 200), GET /v1/mcp-servers and GET /v1/mcp-servers/:name carry the entry's metadata only, with no headers, no env and no owner, for every API-key label and for an entry registered before ownership. On an owner PUT each map is handled on its own: an omitted map keeps the stored one (so reqlift's enable/disable toggle, edit form and schema editor, which send no maps, keep both), a non-empty map replaces it and {} clears it; a new registration that omits a map stores none. A URL or command edit within the same transport family therefore keeps the stored credential. A change between http/sse (headers) and stdio (env) while a non-empty stored map (including one the old transport did not use) is not named in the body is refused with 400 {"error":{"code":"MCP_CREDENTIAL_MAP_INAPPLICABLE","message":"The stored <property> map does not apply to <transport> transport: send <property>: {} to clear it or a new <property> map to replace it"}} and nothing changes; the text never holds a value. Runs, /call, /test, the upload relay and /health still use the real stored values. The args of a stdio server and credentials embedded in a url are still returned.

Credential relay: every registered server (http, SSE and stdio) reaches the agent runtime only as { "type": "http", "url": "http://127.0.0.1:<port>/mcp/<token>" } (server name and every mcp__<server>__<tool> name unchanged); registry args, env, headers and override values never reach the runtime's command line. The relay holds the run's binding (upstream, merged headers or env, grant) until the run ends; the token is revoked at run end or cancel. An upstream refusal never starts an OAuth login inside the gateway: a refused tools/call becomes a TOOL_AUTH_UNAVAILABLE tool result, a refused initialize leaves the server's tools out of the run, and other failures answer with the matching tool error. Only the MCP endpoint is forwarded; the GET event stream answers 405. If the relay is not listening, registered servers are left out of the run (mcp.server.omitted ... reason=relay_unavailable). Details: Tool Mediation. The runtime's own log files are written to a per-run directory that is deleted after the run; DEBUG_CLAUDE_AGENT_SDK is ignored with a startup warning.

requireUserCredentials: a run gets a flagged server only when its mcpCredentialOverrides entry has at least one non-empty value for the transport's target (headers for http, env for stdio) and, with a userCredentialSchema, a value for every output key; an empty entry counts as missing. A headers output key matches override headers in any casing (authorization is satisfied by an Authorization header) and counts only when at least one header matches and every matching header is non-empty; env output keys must match exactly. Otherwise the server and its tool pattern are left out of the run (a request server with that name is refused with 400 MCP_SERVER_NAME_CONFLICT, like any registered name), and the gateway logs mcp.server.omitted serverName=<name> reason=missing_user_credential. Stored and returned only when sent; a PUT without it clears it; /restart keeps it.

Registry ownership

Every entry records its owner, the API-key label of the caller that created it; the owner is persisted with the definition, survives a restart and is never returned by any route (an owner in a request body is ignored). PUT and DELETE of an existing name succeed only for the owner. Any other label gets:

HTTP 403
{"error":{"code":"MCP_SERVER_OWNER_MISMATCH","message":"MCP server \"<name>\" is registered by another application"}}

The answer is the same for PUT, DELETE, an entry owned by another label and an ownerless entry, and never names the owner. The check runs before the name rule and any body validation. Entries registered before ownership are ownerless: refused for every label, left out of a run that carries a user credential for them (mcp.server.omitted ... reason=ownerless) and refused with the same 403 on /call, /test and /uploads/* when the caller sends a credential. The operator assigns their owners with MCP_SERVER_OWNERS=<server>:<label>,... at startup (only ownerless entries; read-back line mcp.registry.ownerless count=<n> names=<list> saved=<true|false>); a malformed value stops startup with FATAL config key=MCP_SERVER_OWNERS reason=.... POST /restart stays callable by any label.

Only for a query sent with enforcedTools: always the first event (seq 0), sent once per query (never again on a retry). tools echoes the enforced set, so the caller can confirm this gateway enforced it. Assistant text output (streamed incrementally).

Session Management

Sessions enable multi-turn conversations with the Claude agent. A client provides a sessionId with each query, and the gateway maps it to an internal Claude SDK session UUID.

How Sessions Work

1

Client sends query with sessionId

Client includes a stable sessionId (e.g., "chat-user-42") in the POST /v1/query request body.

2

Gateway resolves session

Sessions are keyed by the API-key label and the sessionId (stored in the additive sessionsByLabel map of sessions.json; public routes and the done event keep the raw id). If the label has a session with the same ID and an earlier successful query confirmed its SDK session, the existing Claude session is resumed using the SDK's resume option with the stored SDK session ID. After each successful query, the gateway syncs the stored SDK session ID with the actual session_id returned by the SDK, ensuring subsequent queries resume the correct conversation. A failed query confirms nothing: the next query with the same client ID starts a fresh Claude session under a new SDK session ID (using the sessionId option), so it neither resumes nor appends to the failed attempt.

3

Session persists across restarts

Sessions are persisted to disk (debounced write to SESSION_PERSIST_PATH). On restart, sessions are restored and expired ones filtered out.

4

Idle cleanup (optional)

If SESSION_IDLE_TIMEOUT_MS > 0, a background timer runs every 5 minutes and removes sessions that have been idle longer than the timeout.

Stateless Queries

Set "useSession": false in the request body to skip session management entirely. A random session ID is generated for the query, and no session state is stored.

Managing Sessions via API

  • GET /v1/sessions -- list the calling label's active sessions (raw ids) with model and lastUsed timestamp
  • DELETE /v1/sessions/:id -- remove the calling label's own session with that id, else an ownerless legacy entry (another label's answers 404)
  • PUT /v1/settings -- configure sessionIdleTimeoutMs

Agent Isolation

Every agent run executes inside its own sandbox (bubblewrap: new user, PID, IPC, UTS and cgroup namespaces, shared network, all capabilities dropped, nested user namespaces disabled and checked at every start). Bash, interpreters, the Read, Write, Edit, Glob and Grep tools, MCP servers that need no credential and sub-agents all run inside it. The gateway keeps its secrets (API keys, provider credential, OAuth tokens, state files, SSH keys) outside.

What a run sees

  • Read-only: the system directories, the Claude runtime, the global CLAUDE.md, skills/, agents/, memory/, commands/, a generated settings.json that keeps only permissions, and every repository under ~/.claude/projects/. Each repository's git configuration is a generated copy with only remote URLs without user info, fetch refspecs, branch settings and core settings.
  • Writable: the conversation's work area /work (the working directory, kept between its turns), the conversation's home /home/node (rebuilt at every start), a private /tmp and this run's log directory.
  • Not visible: .credentials.json, the state files and their .corrupt-* copies, ~/.ssh, legacy transcripts and logs, other conversations' homes, the Docker socket, and every process of the gateway or of other runs.
  • Every bind source is checked without following symlinks (a regular file or directory owned by the gateway user, inside its tree); anything else is left out with an audit log line. Mounted global workspace entries are scanned at every sandbox start for the gateway's own secret values: API keys, provider key, OAuth tokens, registered MCP header and env values, the private-key lines of the key files in $HOME/.ssh and the credential parts of registered webhook URLs (the URL, path tokens, query and fragment values, user info). Files are read in chunks up to 64 MiB; a file that holds a value, cannot be read safely or is larger than 64 MiB is hidden behind an empty file (audit reason=known_value or reason=too_large). A file is read again when the value set changes, or when its size or modification time changes; a start with nothing changed reads nothing. The scan finds verbatim copies only: not base64, hex, compressed or re-wrapped copies, git object stores, one-off sshKey values of a git request, non-armored key formats, values under 8 characters or values of disabled MCP servers, and it does not cover repositories or the per-user skills bundle, which are mounted without this scan. Repositories are read-only in the sandbox, but a clone request against an existing checkout performs git pull; it does not remove untracked files. Keep repository content trusted and remove stale or sensitive files at the source or during checkout.
  • The environment is an allowlist built from nothing. The only provider credential a run holds is a random per-run token for the gateway's model proxy (x-api-key only, POST /v1/messages and /v1/messages/count_tokens only, revoked when the run ends); the proxy adds the gateway's own credential on the way out. Every registered MCP server (http, SSE and stdio) is reached through the credential relay, which keeps its credentials on the trusted side (see Tool Mediation). Runtime tuning variables outside the allowlist (for example MCP_TIMEOUT) are no longer passed on.
  • Clean home: the runtime and the processes it starts read the agent's home by name at every start (the shell snapshot runs bash -l: .bash_profile, .bash_login, .profile, .bashrc; git reads .gitconfig, .config/git/config and the repository at the working directory; the runtime reads .claude.json and .claude/.config.json). The home is therefore rebuilt from nothing before every sandbox start: every home-root entry except .claude is removed without following links, and .claude keeps only the runtime's data (projects/-* transcripts, todos/, plans/, the memory mount point). A file an agent writes in the home lasts until its run ends.
  • Work area: what an agent wants to keep goes to /work (<AGENT_SANDBOX_ROOT>/sessions/<sandboxDirId>/work), the working directory, private to the conversation and persistent between its turns; the transcripts are then in projects/-work/ and resume works. Nothing in it is read as configuration: runs read only the user setting source (enforced runs none), so a .mcp.json, .claude/settings*.json, CLAUDE.md or .claude/agents|commands|skills written there is never loaded. The runtime runs git status in /work at start, so any .git entry at the root of /work (directory, file or link, never followed) is removed before every start; a repository there is not a supported scenario (repositories are central read-only mounts). Removing .git is one layer: git also treats a directory holding HEAD, objects/, refs/ and config as an implicit bare repository, so the sandbox environment carries trusted command-scope git configuration (safe.bareRepository=explicit, core.fsmonitor=false, core.hooksPath=/dev/null) that outranks any file the agent writes. With no repository discovered in /work, the start-time git reads no agent-written file. Repositories below /work are not discovered from there; git run inside them works, with fsmonitor and hooks off, and a bare repository there needs --git-dir.
  • Extensions: commands, agents, skills, output-styles, plugins, hooks and CLAUDE.md are mounted read-only from the workspace, or from an empty trusted stand-in when it has none (their frontmatter hooks and agent mcpServers execute commands: trusted content only).
  • Repositories under ~/.claude/projects/ stay central, read-only and live. Read-only git commands work in them, for example git -C ~/.claude/projects/<repo> show <other-branch>:<path>; git's "dubious ownership" check does not block them (only repositories owned by the gateway user are mounted, and the sandbox keeps that user). A commit or new branch fails with a read-only file system.
  • Global memory: the workspace's memory/ directory, written only through PUT /v1/memory/* (any API-key holder) and mounted read-only into every sandbox: no conversation can write it, so nothing one conversation writes reaches another through it.
  • Run directories: the per-run directory under <root>/runs/ is removed when the request ends, whatever its outcome; a crashed gateway's leftovers are swept at start. Conversation directories (home and work area) are not removed when a conversation is deleted (MVP-7402).

Conversations

A conversation is keyed by the API-key label and the sessionId, and records its owner (the label and the request's user_id, or none) and a random sandbox home name when it is created. Another label using the same sessionId gets its own new conversation (no refusal, nothing learned). Within a label only the exact owner can continue it: a conversation with a user_id and the same one without are different owners, and another user_id gets the "cannot be continued from your account" text with no run and no change. Ownerless entries from before the isolation update keep their raw id and are still refused for every label. One request at a time is processed per conversation. GET /v1/sessions and DELETE /v1/sessions/:id are scoped to the caller's label. Deleting a conversation leaves its home and work area on disk (retention: MVP-7402).

Container security profile and host prerequisites

docker-compose.yml runs the container as node (uid 1000; ./agent_home must be owned by it) with cap_drop: ALL, no-new-privileges, pids_limit: 512, the committed seccomp profile security/agent-gateway-seccomp.json (Docker's default plus clone, unshare, setns, mount, umount2, pivot_root for a process without capabilities) and systempaths=unconfined (Docker's masked /proc paths make the sandbox's own /proc mount fail). This loosens the boundary between container and host, so every other control above is on. Host prerequisites: unprivileged user namespaces allowed (kernel.apparmor_restrict_unprivileged_userns=0 on Ubuntu 24.04 and later, user.max_user_namespaces above 0). Docker's default AppArmor profile also blocks the sandbox's mounts: by default the compose file runs without an AppArmor profile; to keep one, load security/agent-gateway-apparmor (sudo apparmor_parser -r security/agent-gateway-apparmor) and start with AGENT_GATEWAY_APPARMOR_PROFILE=agent-gateway-isolation. Tested once (2026-10-01, Ubuntu 24.04, kernel 6.8, Docker 29.2): a task-owned container under a copy of this profile loaded with a different name (identical rules; only the profile name and its two self-references differ) ran in enforce mode with isolation: ok, and a cancelled run, docker stop during a run and a SIGKILL of the gateway process behaved as without a profile. The committed file under its own name and other kernels are not tested; PROBE_APPARMOR_PROFILE=<loaded profile> npm run probe:docker-isolation repeats the check.

Rollback. A valid rollback target is an image whose commit and digest passed this acceptance suite and both Docker probes: the revision that contains the isolation (S1), the tool mediation (S2) and the registry ownership (MVP-7925) together, identified by the tag and digest recorded in step 3 of Prepare and in the evidence JSON, not by /health alone. An image with the isolation only also reports isolation: ok, but it puts MCP credentials on the runtime command line and ignores AGENT_TOOL_POLICY. A revision from before the isolation is not a rollback target: it restores unrestricted agent execution. Stop the gateway instead (docker compose stop) and decide explicitly.

To roll back to a recorded tag: docker tag agent-gateway:rollback-<tag> agent-gateway-agent-gateway:latest && docker compose up -d --no-build, then repeat the Verify table (isolation ok, the digest equals the digest recorded for that tag).

At the first deploy of this Epic no valid target exists. Recovery is then to stop the gateway (docker compose stop) and fix forward; callers see connection refused while it is stopped, and the operator decides that before deploying.

Data effects of moving between revisions of the Epic: an older version ignores and then drops the sessionsByLabel map of sessions.json, so conversations started or moved under the newer version start fresh; registered tools and MCP servers keep their owner field, which older versions do not use (they would let any label change or delete a registered server).

Running the acceptance (pre-merge checks). There is no CI in this repository: the required checks are these commands, run by the author before a merge and recorded in the pull request. npm run build && npm test for every change (the real-process security files are part of npm test). In addition both Docker probes, npm run probe:epic-integration and npm run probe:docker-isolation, for every change that touches one of these paths: src/sandbox*.ts, src/agent.ts, src/model-proxy.ts, src/mcp-*, Dockerfile, docker-compose.yml, entrypoint.sh, security/*, scripts/*probe*. A missing prerequisite fails with a fixed host prerequisite missing: <name> line; a suite never skips. Run heavy checks through the workflow kit's scripts/run-verification.mjs --wait --cwd <worktree> -- <command> from a detached worktree at the committed revision, so an edit while a run waits in the queue cannot invalidate it (the runner serializes expensive runs across sessions of the same user).

Reading the evidence. Every security row prints one line; the suites and the probe print only case names, booleans and counts, never a secret value:

grep -a '^SECURITY-' <runner log>
# SECURITY-EVIDENCE: revision, tree, runtime versions, non-secret configuration, deadlines
# SECURITY-MATRIX:   one per row: id, expected, observed, result, hits, duration, deadline, controls, surfaces with byte counts

Behavior changes

  • Global directories and repositories are read-only for agents: an agent can no longer write to ~/.claude/memory, skills, agents or a repository. The workspace API (PUT /v1/memory/*, the git routes) stays the write path; a prompt that tells an agent to update memory files there fails until it uses the API.
  • An agent has no ~/.ssh, and there is no agent-side ssh mediation (no caller uses it).
  • claude auth status does not exist in the bundled CLI: GET /v1/auth/status is read from the credential files with the same fields, and login runs the CLI bundled with the SDK. The entrypoint no longer installs a CLI and no longer runs as root.
  • Workspace listings and user-skill bundles list and copy regular files only (a symlink is neither listed nor followed).
  • Tool mediation (MVP-7679):
    • allowedTools now narrows the trusted grant instead of only pre-approving tools; [] means no tool at all.
    • A tool_result event of a failed call carries "success": false; reqlift's admin tool success rate drops after the deploy because failed calls stop counting as successes.
    • Failed tool calls end in the fixed TOOL_* texts; the refusal text of enforcedTools is the TOOL_DENIED text (it was Refused: this tool is not allowed for this run.).
    • AGENT_MCP_TOOL_TIMEOUT_MS adds an overall deadline (default 600 s) to a mediated MCP tools/call; the relay used to have only its 120 s no-progress timeout, which stays.
    • The relay buffers and validates upstream answers and returns each as one JSON message; it forwards only methods the grant allows.
    • Conversations and the event cache are keyed by API-key label.
    • A request mcpServers entry named like any registered server answers 400 MCP_SERVER_NAME_CONFLICT.
    • allowedToolsPattern of a registry server has no authorization effect.
    • Stdio MCP servers run in their own tool sandbox and see only /usr and the system directories, so their command must live there.
    • Registered webhook tools record an owner; a run is offered only its own label's tools plus legacy ownerless ones.

Known residuals

  • The sandbox shares the network namespace: agent code can reach network peers, credential-free MCP servers and the gateway's public port (where it gets 401 without a key). Loopback listeners of the proxy and relay need a run token.
  • There is no agent-side ssh mediation (no caller uses it).
  • Registry ownership covers PUT and DELETE only: POST /v1/mcp-servers/:name/restart stays callable by any label, any label's run or direct call may still use another label's owned server with its own users' credentials, and the stored headers and env are write-only (MVP-7936): the registry routes never return them, while the args of a stdio server and credentials embedded in a url are still returned and error texts of /health, /test and /call can quote a stored header value that never passed PUT validation. When an owner deletes its server another label may register the same name.
  • Content planted before the deploy: the global-entry secret scan covers files up to 64 MiB, the $HOME/.ssh private-key lines and webhook URL credentials (MVP-7919), as verbatim copies only (the limits are listed in the sandbox content section). The gateway's own trusted git calls and /v1/auth/login still run with HOME=/home/node and read configuration planted there before the update (~/.gitconfig, repository hooks, core.fsmonitor, ~/.tmux.conf); MVP-7679 closed the sandbox-side git reads, the gateway-side ones are owned by MVP-7948 and not fixed. The operator reviews or removes that content before the first deploy.
  • Legacy webhook tools without an owner keep today's forwarding until they are registered again.
  • A credential-free request MCP server runs inside the agent sandbox and is granted per server only: a grant that names only some of its tools is not enforced on the trusted side.
  • Global agents, skills and commands are trusted content (their frontmatter hooks and agent mcpServers execute commands): an agent cannot write them, but any API-key holder can write global agents and skills through PUT /v1/agents and PUT /v1/skills, and those load in ordinary runs. Reachable by callers, not by agent code; not fixed here.
  • A file an agent writes in its home is rebuilt away only at the next start, so a process of the same run (for example a shell the agent starts itself when Bash is granted) can still read it; no trusted step does.
  • Conversation homes and work areas are never removed (MVP-7402), there is no size cap on a home or a private /tmp, and pids_limit is shared by all runs: an availability risk, not a credential exposure.
  • An ownerless pre-update conversation id stays visible: a refusal versus a fresh conversation reveals that such an id exists.
  • The gateway process can exit when a client closes its connection while a hook or an in-process tool call is in flight (SDK 0.1.77 handles control requests unawaited; pre-existing, tracked as MVP-7866). The acceptance cancel row cancels during a Bash call, which is not that path, and does not claim it closed.
  • The runtime in the sandbox shares the network namespace and can make its own credential-free calls to its vendor host (egress residual, TD-9 of the Epic). The acceptance records non-loopback destinations held by the gateway's processes and runs the negative controls offline; it does not block them.
  • The known-value scan hides a mounted file that holds a secret value the gateway knows now. A copy of a credential value that was rotated before the run (for example an OAuth token before a refresh) is not recognized; the scan compares current values.

Tool Mediation

Every tool call that needs a credential leaves the agent sandbox through a trusted channel (the in-process webhook server, a relay binding, an SSE bridge or a stdio tool sandbox). The channel is bound to the run, so identity and credential come from the trusted side, never from a field the agent sends. The agent gets only the tools its grant allows.

Tool policy (AGENT_TOOL_POLICY)

AGENT_TOOL_POLICY='{"default":{"allow":["Read","Grep","mcp__agent-gateway-tools__*"]},
  "labels":{"cicd":{"allow":["Read","mcp__jira__*"],"deny":["mcp__jira__delete_issue"]}}}'
  • An entry is a built-in tool name (case-sensitive; the 18 names of the pinned runtime Claude Code 2.0.77: AskUserQuestion, Bash, Edit, EnterPlanMode, ExitPlanMode, Glob, Grep, KillShell, LSP, NotebookEdit, Read, Skill, Task, TaskOutput, TodoWrite, WebFetch, WebSearch, Write), mcp__<server>__* or mcp__<server>__<tool>. Webhook tools are tools of the server agent-gateway-tools.
  • Deny beats allow. An absent allow means everything a run gets without a policy; allow: [] means nothing. A label entry replaces default for that label. An empty or unset value means no restriction.
  • Startup stops with FATAL config key=AGENT_TOOL_POLICY reason=<reason> for must be a JSON object, unknown field, label not in API_KEYS, unknown built-in tool name or invalid tool pattern. One startup audit line per label lists its effective built-ins and server patterns (names only).
  • Operator warning: removing or renaming a label in API_KEYS while the policy still names it stops the gateway at startup; because the container restarts automatically it keeps restarting. Update both settings together.

Effective grant and enforcement

Effective grant = the policy for the caller's label intersected with the caller's own narrowing (enforcedTools: the exact set; or allowedTools: names and mcp__<server>__* patterns). An omitted list uses the policy grant, an explicit [] grants no tool, and a caller can only narrow. A configured agent, skill, prompt or sub-agent never adds authority. allowedToolsPattern of a registry server is not part of the grant.

  • Built-in tools are enforced by what the runtime is offered (tools and disallowedTools): a built-in outside the grant is refused by the runtime itself for the main agent, a configured agent, a skill, a sub-agent and a resumed conversation, even under the permission-bypass mode the gateway always uses. The runtime's own text for such a refusal is <tool_use_error>Error: No such tool available: <name></tool_use_error> (not changeable).
  • Offered but not granted (a tool of an attached MCP server) is refused at call time with the TOOL_DENIED text, before any upstream request. A server with no granted tool is not attached.
  • Credential-free request servers that run inside the agent sandbox are granted per server only; a grant naming only some of their tools is not enforced on the trusted side.

Relay message rules. A body that does not parse as strict UTF-8 JSON (BOM, other encodings), every batch and every message without a method are refused locally. Allowed methods: initialize, ping, tools/list, the client notifications notifications/initialized|cancelled|progress|roots/list_changed, and tools/call only with params.name exactly in the grant. resources/*, prompts/*, completion/* and anything else pass only when the grant covers the whole server (mcp__<server>__*). Every refusal is answered locally with zero upstream requests. The relay buffers and validates the upstream answer and returns it as one JSON message. For a server whose credential schema composes headers/env and a run that carries no value, tools/call is answered TOOL_AUTH_UNAVAILABLE ("no credential") before any upstream request (the handshake still goes upstream); requireUserCredentials omission is unchanged.

One header merge for relay, SSE bridge, direct call and test: the per-user value replaces the shared header of the same name in any casing. There is no broader-credential fallback, no OAuth login and no redirect is followed (webhook, relay, SSE bridge, direct call, test, health). The SSE bridge accepts the endpoint event only on the registered origin (otherwise the redirect text; the credential is never sent elsewhere), answers server requests locally (ping with {}, roots/list with no roots, others method-not-found) and drops server notifications.

Stdio tool sandbox. Every registered stdio server (with or without env), stdio overrides and request stdio servers with env run in their own sandbox: own user, PID, IPC, UTS and cgroup namespaces, a private empty home and /tmp, read-only system directories only and no gateway content. The environment is HOME, USER, PATH, LANG, LC_*, TERM, TMPDIR plus the server's own env after overrides, never the model proxy token or URL or the run-log path. It starts with the run's first message within ISOLATION_STARTUP_TIMEOUT_MS, is restarted once if it dies before answering initialize, is killed on revoke, cancel or gateway stop (--die-with-parent), and its stderr is discarded. A stdio server sees only /usr and the system directories, so its command must live there.

  • rsync, wget, curl, jq, mc, python3 -- general utilities
  • bubblewrap, util-linux -- the per-run agent sandbox and its start check (unshare)
  • tini -- init process (process 1): forwards stop signals to the gateway, reaps finished child processes, returns the gateway's exit code
  • Claude Code CLI -- the copy bundled with the Agent SDK (runs the agents and the OAuth login); nothing is downloaded at startup

Entrypoint Behavior

The whole container runs as the node user (user: node in docker-compose.yml; ./agent_home must be owned by uid 1000). There is no root step:

  1. Creates workspace directories (~/.claude/memory, ~/.claude/agents, ~/.claude/skills, ~/.ssh)
  2. Writes default Claude settings with broad tool permissions (if not already present)
  3. Restores SSH key config from bind-mount if keys exist in ~/.ssh/
  4. Starts the Express server

Stopping the Container

The image entrypoint is ["/usr/bin/tini", "--", "bash", "/app/entrypoint.sh"], so docker stop, docker compose down and host shutdowns deliver SIGTERM to the gateway, and the container's exit code is the gateway's. docker-compose.yml needs no init: setting. On the signal the gateway refuses new connections, saves pending changes at once, lets requests already received finish for up to 8 s (streams still open then are cut), saves all state again and exits. A second signal skips the wait. See State Files, Recovery and Shutdown for the exit codes.

Persistent Data

The agent_home directory is bind-mounted at /home/node and stores:

  • /home/node/.claude/sessions.json -- session state, including the per-label sessionsByLabel map (survives container restarts)
  • /home/node/.claude/tools.json -- registered tool definitions with their owner (survives container restarts)
  • /home/node/.claude/mcp-servers.json -- external MCP server registry (survives container restarts)
  • /home/node/.claude/skills/ -- published skills
  • /home/node/.claude/agents/ -- agent configurations
  • /home/node/.claude/memory/ -- workspace memory
  • /home/node/.claude/projects/ -- Claude session data
  • /home/node/.ssh/ -- SSH keys (uploaded via POST /v1/ssh-keys)

Embedding in an Existing Stack

To add the Agent Gateway as a service in an existing docker-compose.yml:

services:
  agent-gateway:
    build: ./path/to/agent-gateway
    container_name: agent-gateway
    ports:
      - "127.0.0.1:3001:3001"
    volumes:
      - ./agent_home:/home/node
    environment:
      - ANTHROPIC_API_KEY=${ANTHROPIC_API_KEY}
      - API_KEYS=${API_KEYS:-default:changeme}
      - LOG_LEVEL=${LOG_LEVEL:-info}
      - SESSION_PERSIST_PATH=/home/node/.claude/sessions.json
      - TOOLS_PERSIST_PATH=/home/node/.claude/tools.json
      - MCP_SERVERS_PERSIST_PATH=/home/node/.claude/mcp-servers.json
      - SESSION_IDLE_TIMEOUT_MS=${SESSION_IDLE_TIMEOUT_MS:-0}
      - AGENT_TOOL_POLICY=${AGENT_TOOL_POLICY:-}
      - AGENT_MCP_TOOL_TIMEOUT_MS=${AGENT_MCP_TOOL_TIMEOUT_MS:-}
      - MCP_SERVER_OWNERS=${MCP_SERVER_OWNERS:-}
    healthcheck:
      test: ["CMD", "curl", "-sf", "http://localhost:3001/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s
    restart: unless-stopped

Other services can reach the gateway at http://agent-gateway:3001 on the Docker network. The port 127.0.0.1:3001 binding ensures it is not exposed publicly -- use a reverse proxy (nginx, Traefik) for external access with SSL.

Reverse Proxy (nginx)

location /agent-gateway/ {
    proxy_pass http://127.0.0.1:3001/;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_buffering off;           # Required for NDJSON streaming
    proxy_read_timeout 300s;       # Agent queries can be long-running
}

Important: disable proxy buffering

NDJSON streaming requires proxy_buffering off in nginx. Without it, events are buffered and delivered in batches instead of real-time. The gateway also sets X-Accel-Buffering: no on streaming responses as a fallback.

Architecture

Request Flow

1

HTTP Request

Client sends POST /v1/query with Bearer token, queryId, prompt, and optional sessionId.

2

Auth Middleware

Validates API key against API_KEYS env var. Attaches client label for audit logging. Rejects with 401 if invalid.

3

Session Resolution

Looks up or creates a Claude SDK session under the caller's API-key label and sessionId. Reuses the label's existing session if prompt and model match; creates a new one if first query or config changed. Then the tool grant is computed: the policy for the label intersected with the caller's enforcedTools or allowedTools.

4

Agent SDK Execution

Runs query() from Claude Agent SDK in the run's sandbox with the granted tools (default: Bash, Read, Write, Edit, Glob, Grep, WebSearch, WebFetch, Skill, TodoWrite). Credential-bearing tools go through the trusted relay, bridge or webhook channel, which checks the grant before any upstream request. Streams events via NDJSON as the agent works.

5

Retry Layer

On rate limits, overloads or empty answers: exponential backoff (1s, 2s, 4s), up to 3 retries, 60s total budget. Emits rate_limited events to the client. Permanent failures (runtime too old, authentication, unknown) end at once with one error event. A retry resumes only a session an earlier successful answer established; otherwise it starts fresh under a new SDK session ID.

6

Event Cache + Done

All events are cached by label and queryId for replay via GET /v1/query/:id/events (only the starting label can replay). Cache entries expire after 30 minutes (configurable). Final done event includes token usage and cost.

State Files, Recovery and Shutdown

sessions.json (with the idle-timeout setting), tools.json and mcp-servers.json are written by src/persistence.ts: a temp file <file>.tmp-* (mode 0600, same directory) is written and flushed, then renamed over the file, so a kill, crash or full disk leaves either the complete old file or the complete new one. On start, a missing file is an empty start; a file that cannot be read or parsed, or that holds an entry the gateway cannot restore (null, a tool or MCP server without a string name, a session without a numeric lastUsed), is moved to <file>.corrupt-<UTC stamp> and reported, never overwritten. If it cannot be moved, it stays in place and saves for that area are switched off until a restart loads it. Each problem is reported by /health and logged, whatever the log level, as ERROR persistence area=<area> problem=<problem> file=<path> [preservedAs=<path>] reason=<fixed text> [code=<errno>] (see /health); the line never contains file content.

Shutdown sequence (src/shutdown.ts)

  1. First SIGTERM/SIGINT: stop accepting connections, save every pending change at once.
  2. Drain: requests already received, including streaming chat answers, run on and may change state.
  3. When the last connection has closed, after 8 s, or on a second signal: close remaining connections and save all three files synchronously. Nothing can change between this save and the exit.
  4. Exit 0 if every final save succeeded, 1 otherwise (an ERROR persistence … problem=final-save-failed line names the area; its file keeps its last complete save; check docker logs, disk space and permissions). 137 (killed by Docker after 10 s) is still possible while a git command blocks the gateway, until MVP-7614 is deployed; the files stay intact, but changes from the last moment can be lost.

Recovering a .corrupt-* copy

  1. The container path /home/node/.claude/<file> is ./agent_home/.claude/<file> on the host.
  2. Stop the gateway first; otherwise its next save overwrites the restored file.
  3. The copy is usually damaged, or it holds an entry the gateway cannot restore. Repair it (cut back to the last complete entry and close the array or object, or fix or remove the entry that is null, has no string name or, for a session, no numeric lastUsed; check with jq) and copy it over <file>. This replaces the changes made in that area since detection. A copy kept after a read error has its original permissions; fix them first.
  4. Give the restored file node:node ownership (chown 1000:1000) and its original mode (for example chmod 600 for mcp-servers.json).
  5. Move the copy out of the directory or delete it; only this clears degraded.
  6. Start the gateway and confirm with curl -s http://localhost:3001/health | jq '.persistence, .persistenceIssues'.

Copies of mcp-servers.json contain MCP credentials: handle them as secrets, never attach state files or copies to tickets or evidence, and delete them once resolved.
