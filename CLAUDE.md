# CLAUDE.md -- Agent Gateway

## Project Overview

Standalone REST API service wrapping the Claude Agent SDK. Exposes Claude Code's agentic capabilities (by default Bash, Read, Write, Edit, Glob, Grep, NotebookEdit, WebSearch, WebFetch, Skill, Agent, TodoWrite; the bundled runtime is Claude Code 2.1.292, and a policy can enable any other tool it offers for one label) over HTTP with NDJSON streaming, session management, and automatic retry with exponential backoff.

**Tech stack**: Node.js 22, TypeScript, Express 5, Claude Agent SDK, Docker

## Development Commands

```bash
npm run build       # TypeScript compile (tsc)
npm run dev         # Dev server with hot-reload (tsx watch)
npm start           # Production start (node --expose-gc dist/server.js)
npm test            # Unit tests (vitest, excludes E2E)
npm run test:e2e    # E2E session tests (requires running Gateway + GATEWAY_API_KEY env var)
npm run probe:docker-isolation  # Docker Outcome Probe: builds the image, runs task-owned containers under the compose security profile (needs sudo -n docker, uid 1000)
npm run probe:docker-stop       # Docker Outcome Probe for the clean stop (same profile)
npm run registry-url-inventory -- <mcp-servers.json>  # Rollout inventory (MVP-7957): names and categories of registry entries whose stored URL breaks the public-URL rule (never a URL; exit 0 none, 3 some, 2 unreadable); needs `npm run build`
npm run probe:epic-integration   # Epic Integration Gate (MVP-7677): task-owned container on an --internal network, OAuth mode, representative reqlift and diemcrm callers, the eight secret routes before and after docker restart (needs sudo -n docker, uid 1000; writes an evidence JSON with the image digest)
```

## API Key Format

```
API_KEYS=label1:secret1,label2:secret2
```

Keys are sent as `Authorization: Bearer <secret>`. The label is used for audit logging and scopes sessions, the event cache and registered tools. A label named in `AGENT_TOOL_POLICY` must stay in `API_KEYS`: removing or renaming it alone stops the gateway at startup (and the restart policy keeps restarting it), so change both settings together.

## Isolation Rules (MVP-7678)

Every agent run executes in a bubblewrap sandbox (`src/sandbox.ts`, `src/sandbox-content.ts`). When you change anything near it:

- **Never pass `process.env` (or a copy of it) to the runtime.** The SDK `env` option and the spawn hook get only `runtimeEnvFrom(...)` plus the per-run log variables; the sandbox builds its own allowlist in `buildSandboxEnv`. A new variable the runtime needs is added to that allowlist with a test that asserts the exact key set (`sandbox.test.ts`, `sandbox-process.test.ts`), never inherited.
- **The only provider credential a run holds is its model proxy token** (`ANTHROPIC_API_KEY=<run token>`, `ANTHROPIC_BASE_URL=<loopback proxy>`). The real key and the OAuth tokens stay in `model-proxy.ts` on the trusted side.
- **No-follow rules.** Every path the trusted side binds into a sandbox, copies, lists or reads from agent-writable storage is checked with `lstat`/`O_NOFOLLOW` (`checkTrusted`, `readFileNoFollow`, `listRegularFilesNoFollow`, `copyFileNoFollow`): a regular file or directory owned by the gateway user, inside its expected tree, whose real path is the path itself. Never use `existsSync`, `statSync`, `copyFileSync` or `realpathSync`-then-use on such a path. Mount points inside a conversation home are sanitized with `prepareMountPoints`.
- **Fail closed.** A start problem must end in an `IsolationFailure` (fixed text, not retried); nothing may fall back to an unsandboxed run. The launch wrapper refuses what it cannot prove (MVP-8020): a descriptor above 2 that survived the close (exit 94, `start_failed`), a check tool (`/usr/bin/unshare`, `/usr/bin/true`) that is not a regular executable file or an `unshare` that could not run (exit 95, `binary_missing`), no descriptor listing (96, `proc_denied`), nested user namespaces still possible (97, `userns_not_blocked`). A new precondition of the wrapper gets an exit code, a classifier row and a real-process row with a control that shows the check is live. New fixed texts go through `run-failure.ts` and are asserted verbatim.
- **A conversation belongs to its API-key label, not to a person** (DEC-ISO-007, MVP-8044). Admission looks at the label only: any `user_id` of the label, null or present, continues the conversation; never reintroduce a same-label `user_id` comparison, and never read the stored `owner.userId` for a decision. The request's `user_id` stays per request (the writer's skills, the webhook context, the per-request credential overrides): nothing of the creator's carries over, and a writer without a credential never gets the creator's. Another label never sees the conversation; ownerless pre-update entries stay refused (`SESSION_LEGACY_MESSAGE` and `SESSION_BUSY_MESSAGE` are pinned byte for byte, reqlift matches them). The rows are `AD.same-label-writer`, `AD.other-label` and `AD.relay-token-replay` with four negative controls.
- **Trusted files never enter a sandbox**: `.credentials.json`, state files, `~/.ssh`, other homes. New trusted state needs a test row that proves it is absent from a real sandbox (with a control that proves the probe works) and a synthetic marker, never a real secret.
- Real-process tests that start sandboxes and runtimes run through the workflow kit's `scripts/run-verification.mjs`; clean up only your own temp directories and containers.

## Security Acceptance Rules (MVP-7677)

- **Pre-merge rule.** There is no CI: a change is mergeable when `npm run build && npm test` passes, and, if it touches `src/sandbox*.ts`, `src/agent.ts`, `src/model-proxy.ts`, `src/mcp-*`, `Dockerfile`, `docker-compose.yml`, `entrypoint.sh`, `security/*` or `scripts/*probe*`, when `npm run probe:epic-integration` and `npm run probe:docker-isolation` pass too. Record the commands and their runner result lines in the pull request.
- **Use the workflow kit's runner for heavy runs:** `node ~/jira-workflow-kit/scripts/run-verification.mjs --wait --max-wait-minutes <N> --cwd <worktree> -- <command>` as ONE background command, from a detached worktree at the committed revision (hardlinked `node_modules`, a fresh `tsc`): the runner tests the live directory it is given, so an edit during a queue wait invalidates the run. Never poll its exit 75 in a loop.
- **Test gateways get a reserved port and the shared readiness wait (MVP-8129).** A spawned gateway's port and every "nothing listens here" port come from `reserveGatewayPort()` in `src/tests/helpers/git-process-gateway.ts` (8192 ports below `ip_local_port_range`, one 256-port slot per vitest pool id, a lock file per port under `<tmpdir>/agent-gateway-test-ports/`, then a bind check), never from `listen(0)` + `close()`: any other `listen(0)` on the host can take that number before the gateway binds it. A start waits through `waitForGatewayReady()`: `/health` answers 200 AND the child pid itself owns the LISTEN socket, bounded by `GATEWAY_READY_TIMEOUT_MS` (45 s); an exit rejects at once with the exit code, the signal and the last 20 redacted log lines. A test or hook budget covers 45 s + 15 s for each gateway start. `GATEWAY_STARTUP_LOG=<file>` makes every start append one line (`ready|failed|milestone pid= port= ms=`). `gateway-startup-process.test.ts` row S7 fails when a test file keeps its own readiness loop or port pick.
- **A new isolation vector needs a row, not a list entry.** Add a row to `security-regression-process.test.ts` (or the matching security file) with a stable AC id in `AC_ROWS`, a permitted control that shows the route is live, and the five surfaces; `security-matrix.test.ts` checks that every id a suite requires is in the map. Security files never `skipIf`: a missing prerequisite throws `host prerequisite missing: <name>`.
- **A sampler exemption needs a real-process control that fails without the narrowing** (MVP-7992). The process sampler (`startProcessSampler`) excuses a `cli.js` candidate only by its executable (device and inode of a known launcher), never by `comm`, argv or ancestor names, and re-checks it on every tick; a live process whose executable cannot be read stays counted. A new or widened exemption comes with a row in `security-matrix.test.ts` ("process sampler launcher exemption") that runs a renamed stand-in outside the sandbox, first asserts the sampler recorded it, and must fail when the exemption is widened to a name; `stop(markers)` takes the run markers, and audit and problem lines print only allowlisted process and flag names. **Exit rule (MVP-8090):** a failed proof on a tick where the runtime is confirmed to be ending is cleared only by a proof read while a process was alive (`exitProofClears`: the runtime's own full proof at an earlier tick, or a live ancestor that is the real bwrap by executable and has the full proof itself), never when the failed read showed the gateway's pid or user namespace, and never resets an earlier flag; an unreadable mount namespace, a broken chain, an unreadable executable or a `bwrap` name clears nothing. Its controls are the rows E1 to E5 of that describe, G1 and G2 of `security-failure-process.test.ts` (the exit is forced through the `afterStableReading` seam, which has no effect by default) and the decision table; a widened rule must turn one of them red. **Reference rule (MVP-8090 rev 3):** the sampler compares the runtime's namespaces with the gateway's, so the gateway's own identity is measured, not assumed: its `ns/{pid,user,mnt}` are cached per pid and start time while it is healthy, every comparison reads the live link first and uses the cache only when the live link cannot be read (a live link that differs from the cache fails the window), and the runtime side is never cached. When the gateway itself ends, a failed proof can only be explained by that: the record is `pending` (still counted as flagged) and is cleared only when the runtime had its own full proof earlier, the gateway is ending (ended, or a zombie leader that still shows threads for a few milliseconds), nothing the runtime reads equals the cached gateway, and within 2 s both the runtime's own exit and the gateway's end are confirmed; otherwise it stays flagged (a gateway that stays a zombie leader with running threads expires as `expired-reference`). **Runtime-side rule (MVP-8090 rev 3.2):** the native runtime is multi-threaded, so on a normal exit its leader thread finishes first (its mount namespace link becomes unreadable and its command line empty) and the process is a zombie that still counts threads for a few milliseconds. Such a record is `pending` (counted as flagged) only when the runtime had its own full proof earlier, one of its own namespace links is the unreadable one, and nothing it reads equals the gateway's; it clears only when the process fully ends (a confirmed kind of the thread-safe exit rule below) within 2 s, otherwise it expires flagged. A live runtime is never read as ending (control R9 calls the exact classifier on a live process; the unprivileged test cannot produce a live runtime with unreadable own links, so that chain stays a decision-table row). **Launcher-ended rule (MVP-8125):** the gateway stops only the outer bwrap (gateway exit, cancel, deadline stop, dispose timeout, start failure), so the inner bwrap (pid 1 of the sandbox) is reparented to the user's subreaper and the runtime below it leaves the gateway's tree; the one tick whose snapshot predates that proves the runtime through a broken chain while the gateway and the runtime are alive. Such a record is `pending` (counted as flagged) only when ALL of these hold (`launcherEndedPending`): the runtime had its own full proof earlier (`ownProofHeld`); its direct parent is the very process, by pid and start time, that was recorded at a proven tick as the real bwrap by executable (`launcherIdentityOf` is `verified`; the identity is overwritten with `none` on every proven tick whose parent is not the real bwrap); that parent reads now as the real bwrap or as `gone` (ENOENT together with an empty command line: the inner bwrap in its own exit; EACCES, ESRCH, any other error and another executable never qualify, `launcherExeOf`); it is in the tick's snapshot (pid and start time) and its own parent is neither the gateway nor a snapshot process (it left the gateway's tree); the gateway is alive and has a verified cache; all three of the runtime's own namespace links read at the proof; nothing it reads equals the gateway's; and the exit read that follows the proof finds the runtime alive or a thread-group leader that finished while other threads run (`Zn` or `empty-n`: a multi-threaded runtime whose leader finished between the two reads, QA of MVP-8125, MVP-8130). The parent is read as stat, executable, command line, stat. `launcherLeftTree` (snapshot membership by pid and start time, the launcher's parent neither the gateway nor a snapshot process) and `launcherEvidenceOf` (the only builder of the route's input: escape evidence, the gateway's re-read, the cache, the exit read, the launcher's identity and position) are exported and used by the sampler itself. It clears only when the runtime's own exit is confirmed by pid and start time within 2 s (no condition on the gateway; `Zn` and `empty-n` are not confirmed exits, so such a runtime is pending, counted as flagged, and never cleared while it is one of them), otherwise it expires flagged; the precedence stays reference-ended, runtime-ending, launcher-ended, and the launcher-ended route shares no tick with either of the others. Its controls are the rows LE1 to LE7 and LE8-zn / LE8-zn-never of "process sampler launcher ended" (LE8 places the leader's exit between the proof and the exit read with the test seam `afterFailedProof`, which has no effect by default and is called only on a failed proof outside a proven ancestor, with a multi-threaded python3 stand-in), G5 of `security-failure-process.test.ts` (wrapper mode `keep-inner`, which removes only `--die-with-parent`; the control signals only the processes it recorded under the verified sandbox tree: outer = the gateway's own real-bwrap child, inner = the real bwrap whose parent is the outer, runtime = the inner's child, each with its start time re-checked before every signal) and the decision table, including the wiring rows of `launcherEvidenceOf`; a widened rule must turn one of them red. Stated exceptions to the real-process rule: the gateway never ends as the launcher's parent (Node does not set `PR_SET_CHILD_SUBREAPER`, so no real failed-proof tick carries a launcher whose parent is the gateway), and the escape, reference-state and cache terms of the wiring (no real process holds its own proof and reads the gateway's namespaces, `reference-ended` takes precedence while the gateway ends, and the own proof needs the cache taken in the same tick). Residuals that stay flagged: a runtime whose first stable reading falls on the break, one still alive 2 s after it, an inner bwrap whose executable reads EACCES or ENOENT while its command line is still present, another process between the runtime and the inner bwrap, and a live runtime with an unreadable own link. **Thread-safe exit rule (MVP-8130):** a confirmed exit needs the kernel fact that every thread of the process is gone, and a read that proves nothing is `unknown`, never `vanished`. One exit reading reads `/proc/<pid>/stat` first (the state, the thread count `num_threads` and the start time all come from that one text; `/proc/<pid>/status` is not read), then the command line, then the executable, and the sampler decides on a bracket of full readings (`exitBracket`: two agreeing readings decide, up to three pairs; a stat that fails with ENOENT or ESRCH or a new start time decides at once because both facts are monotone, any `unknown` reading decides `unknown`, and a disagreement never yields a confirmed exit unless both kinds were confirmed). The confirmed kinds (`isConfirmedExit`) are `vanished`, `start-changed`, and `X`, `Z1` and `empty-gone` with a thread count of EXACTLY 1 read from the same stat text; `Zn` (state `Z`, more than one thread) and `empty-n` (empty command line, missing executable, more than one thread: a leader that finished while other threads run) are never confirmed and are handled alike by every route (pending-eligible wherever `Zn` is); a count of 0 (a task already released) and a command line read that failed with ENOENT or ESRCH next to a readable stat are read again before any other rule (the next stat normally fails with ENOENT and decides `vanished`) and are `unknown` only if they persist to the end of the budget; `X` or `Z` with a count other than 1 is the old leader of an exec. A stat error other than ENOENT/ESRCH, any command line error, an executable error other than ENOENT/ESRCH/EACCES (also a failed identity read of a readable link) and a missing or non-numeric thread or start field read `unknown` (`exitReadOutcome`). `unknown` is never ending, never a leader exit, never a reference ending, never a launcher-ended entry, and a pending record whose reads stay `unknown` expires flagged. A pending record stores whether a leader-exit reading was seen (`sawLeaderExit`); a later `alive` reading of the same pid and start time, or a live settle reading by pid whose executable differs from the one at the record's last proven tick, is a revival (a surviving thread ran `exec`): the record expires flagged at once (`revived=true`) and nothing clears it. Every clear prints `exit-confirmed=<kind>` (the reference-ended route both kinds), an `unknown` prints `exit-read=<file>:<errno>`, and a sampler window refuses a `/proc` mount with `hidepid` (`host prerequisite missing`: a live process could read ENOENT there). The only new test seam is `exitReadFault` (an errno for one exit read, none by default; EIO, EMFILE, ENFILE, ENOMEM, EPERM and, on stat and command line, EACCES are accepted, ENOENT and ESRCH are refused and read `unknown`, a throwing seam reads `unknown`; records hit by it print `exit-read-injected=true`): it can only push a reading toward `unknown`, and only the rows RE-own, RE-exe, RE-rt, RE-ref, RE-le, RE-launcher, R1-RE, TH-bracket and TH-seam may pass it (`TH-seam: static` scans the test files). Its controls are the decision rows T-th1, T-th2 and RE1 and the real-process rows TH1 to TH3, TH-own-live, TH-own-revive, TH-own-revive-exit, TH-bracket, RE-own, RE-own-control, RE-exe, R6-emptyn, R6-emptyn-never, R6-revive, R6-revive-exit, RE-rt, R5-emptyn, R5-revive, RE-ref, R1-emptyn-never, R1-revive-exit, R1-RE, R1-kind, LE8-emptyn, LE8-emptyn-never, LE8-revive, LE8-revive-exit, LE8-revive-alive-entry, RE-le, R8-emptyn, RE-launcher and E2-kind (the held leader exit is a python3 stand-in whose leader opens fresh files in a private descriptor table before it ends alone, so its exit is held for a measured while; a row whose hold had ended before the exit read finished is INVALID, never a pass); a changed predicate must turn one of them red. Not claimed: (1) for `empty-gone` only, the bracket cannot exclude a clone plus a leader exit between the stat read and the command line and executable reads of both readings with an exec in between (inferred not reachable, not measured; `Z1` and `X` are single-read facts with the exact count); (2) a leader exit, an exec and the full exit of the new image all between two settle reads (under one tick) can still clear, like any process that lives less than one tick; (3) a launcher-ended record that entered `alive` and whose surviving thread re-executes the same executable while every settle read misses the leader-exit window, with the new image ending inside the bound, can still clear (at that moment nothing is alive, and the namespaces were inherited); (4) the live-launcher route has no pending option, so a rare fail-closed false alarm on a native SIGKILL group exit (`R8-emptyn`) is possible; (5) read errors on the sampler's per-tick path (`readProc`, `readExe`) still pause detection for that tick, a detection gap and not a clear (follow-up). "No live runtime is cleared" therefore holds for the exit kinds `exitBracket` confirms. Every summary line names its row (`row=`, `flagged=`): a flagged record outside the rows that expect one is a possible escape, not noise.
- **Evidence prints names and counts only** (`SECURITY-EVIDENCE`, `SECURITY-MATRIX`, `SECURITY-SUMMARY`); never put a marker value into an assertion message, a log line or a Jira comment. A negative control must stay red: its child run exits nonzero against a deliberately vulnerable copy of `dist/` and prints no marker value.
- **Deployment and rollback** follow the README runbook "Security acceptance and deployment runbook": a rollback target is an image that passed the suite and both probes, identified by tag and digest, never by `/health` alone.

## Tool Mediation Rules (MVP-7679)

- **Every run names its built-in tools** (MVP-8088, DEC-ISO-008). `agent.ts` always sets `tools` (the granted built-ins) and `disallowedTools` (the rest of the inventory); without a policy a label gets `APPROVED_DEFAULT_SET` (`Agent` (alias `Task`), `Bash`, `Edit`, `Glob`, `Grep`, `NotebookEdit`, `Read`, `Skill`, `TodoWrite`, `WebFetch`, `WebSearch`, `Write`), never what the runtime offers by default. `RUNTIME_BUILT_IN_TOOLS` in `tool-grant.ts` is the inventory of the bundled runtime as the gateway starts it (`Agent`, `Bash`, `CronCreate`, `CronDelete`, `CronList`, `Edit`, `EnterWorktree`, `ExitWorktree`, `Glob`, `Grep`, `ListAgents`, `NotebookEdit`, `Read`, `ReportFindings`, `ScheduleWakeup`, `SendMessage`, `Skill`, `TaskStop`, `TodoWrite`, `WebFetch`, `WebSearch`, `Workflow`, `Write`, plus the alias `Task` of `Agent`); the policy parser rejects every other name (`TaskOutput`, `LSP`, `AskUserQuestion`, `EnterPlanMode`, `ExitPlanMode`, `KillShell`, `TaskCreate`, `TaskGet`, `TaskList`, `TaskUpdate`, `Artifact`, `SendUserFile`, `ShareOnboardingGuide`, `DesignSync`, `Monitor`, `PushNotification`). `buildSandboxEnv` fixes `CLAUDE_CODE_ENABLE_TASKS=false` (the runtime then offers `TodoWrite`, which reqlift's checklist parses, and not the task tools) and the gateway's environment cannot override it. **A runtime upgrade must pass the committed inventory row** in `builtin-tool-grant-process.test.ts`: it starts the bundled runtime with the gateway's runtime keys and fails, naming the tool, when the runtime adds, removes or re-aliases a built-in; review the new tool against the isolation rules before adding its name to the inventory, and re-measure the set of a general-purpose subagent. The runtime's own default set also depends on the model and on what a run pre-approves (measured: without a model it offers no `TodoWrite`, and `Glob` and `Grep` only appear in it when the run names them), which is another reason every run passes an explicit list. A new built-in is never part of the default set without an operator decision.
- **Never put a credential (header, env, args, override) into the runtime's MCP configuration.** The runtime gets only `{ "type": "http", "url": "http://127.0.0.1:<port>/mcp/<token>" }`; no registry `args`/`env`, override or request `env` value and no header may reach its command line. The debug log redacts the same values: `headers`, `env` and the `args` of a stdio server definition (`logging.ts`, `redactCredentialsForLog`).
- **Loader settings never reach a tool server** (MVP-8020): `buildToolSandboxEnv` removes every `LD_*` key and `GLIBC_TUNABLES` from the server's env, whatever its source, before the launcher and the in-sandbox wrapper start (both would load a library before the descriptors are closed). A caller that needs one has to start its server another way; the README states the compatibility impact. Never log a removed name or value, only the count.
- **Every credential-bearing MCP server (http, SSE, stdio) goes through a relay binding** (token, upstream or bridge, merged credentials, grant). Stdio servers with env run in their own tool sandbox. If the relay is not listening the server is left out of the run, never connected directly.
- **The grant check runs before any upstream request.** Effective grant = `AGENT_TOOL_POLICY` for the caller's label intersected with the caller's narrowing; a caller can only narrow. `allowedToolsPattern` is not part of the grant.
- **The agent can write its own home and its work area**, so nothing the runtime or its children (`bash -l` for the shell snapshot, `git`) read at start may come from them. The home is rebuilt from nothing before every sandbox start (`prepareSandboxHome`): every home-root entry except `.claude` is deleted without following links, and `.claude` keeps only `RUNTIME_WRITABLE_DIRS` (projects, todos, plans, memory) with only `-*` transcript directories below `projects`. The agent's persistent files live in the per-conversation work area `sessions/<id>/work`, bound at `/work` (the working directory, so transcripts are in `projects/-work/`); `prepareWorkArea` removes ANY `.git` entry at the `/work` root at every start (directory, file or link, never followed; a `commondir` pointer or `extensions.worktreeConfig` + `config.worktree` defeats a config-only rewrite), because the start-time `git status` runs there; repositories are central read-only mounts, so a work-root repository is not a supported scenario. Removing `.git` alone does not close the class: git also treats a working directory that holds `HEAD`, `objects/`, `refs/` and `config` as an implicit bare repository (with `core.bare=false`, `core.worktree`, `core.fsmonitor` it runs a command at `git status`). So the sandbox environment carries trusted command-scope git configuration (`GIT_TRUSTED_CONFIG` in `sandbox.ts`, `GIT_CONFIG_COUNT/KEY_n/VALUE_n`, highest precedence): `safe.bareRepository=explicit` (an implicit bare repository is refused, so git discovers no repository in `/work` and reads no agent-written file), `core.fsmonitor=false`, `core.hooksPath=/dev/null`. Repositories below `/work` are not discovered from `/work`; git run inside them works, but their fsmonitor and hooks are off and a bare repository there needs `--git-dir`. Do not add file names to a list: a new vector means a new row that plants it in `/work` and asserts no marker at the next start. `settingSources` is `["user"]` (enforced runs `[]`), so nothing in `/work` is read as configuration; the extension directories (`commands`, `agents`, `skills`, `output-styles`, `plugins`, `hooks`, `CLAUDE.md`) are always mounted read-only, from an empty trusted stand-in when the workspace has none. New agent-writable paths are untrusted by default; do not extend a deny-list or add a persistent home path. Each path the runtime is found to read at start needs a row in `sandbox-home.test.ts` and, for execution, the real runtime. Deleting conversation directories (home and work) is MVP-7402.
- **A `Bash` denial also covers the commands skill, agent and command files start** (MVP-8106). `runQuery` reads the policy-only `Bash` grant of the label once (`computeToolGrant({ label }).allows("Bash")`, the caller's narrowing never decides it) and both command gates key on it: the request-server `command` gate and `neutralizeCommands`. Without the grant `planTrustedContent` binds a run-scoped snapshot of `skills`, `agents` and `commands` (no-follow copy, a bounded walk with file, folder, examined-entry and byte limits and one `sandbox.content.limited` summary line when it stops early, every `.md` rewritten by `command-settings.ts`: the gateway's own block first, the allowlisted keys re-encoded, the original body after it) instead of the live directories, and `materializeUserSkills` writes the per-user bundle rewritten; the stored files are never modified and saving stays allowed. Never copy the original frontmatter or edit it with a deny-list (a setting that gets past a parser difference runs), never bind the live entry for a denied run (the runtime picks up a skill saved while a session is open), and add a new frontmatter key to the allowlist only after measuring it on the bundled runtime (it must start no command and widen no tool set). A new place the runtime loads settings from (`plugins` loads only with `enabledPlugins`, which the generated `settings.json` never holds) needs a row in `command-settings-process.test.ts` and, if it loads, a snapshot entry.
- **A webhook, relay or bridge failure maps to a fixed `TOOL_*` text** (`tool-mediation.ts`), never an upstream body, header, URL or secret. No redirect is followed anywhere.
